The Coco · rung 7

Rules to Settlement

A chain's own validity rule, traced from the block it was sealed in to the verdict it settles — every aggregator function it passes through, which process runs which goal, and what each step leaves behind. The host was never told what any of these chains are: it reads their rules off their blocks and runs them, under the same fence contracts run under.

The claim in one line: in the choreography the aggregator consults a ledger node and an aggregator node and never consults hub/chains.pl. Everything it knows about zeta, omega and psi — what a valid block is, which head is better, what counts as final — it read off their blocks.

01

Rules travel the way data travels

rules_payload/3 → ledger_seal/1 → ledger_sync/1 → rules_of_payload/3

A chain's rules are a block payload. That one decision is the rung: the rules are hash-committed, signed by whoever was entitled to seal, gossiped like anything else and identical on every node that holds the block — and none of it needed a mechanism, because rung 2 already does all of that for payloads.

  1. 1The chain seals its own rules. Six clauses for zeta: a validity rule, two authority keys, two fork-choice clauses and a finality rule. rules_payload(zeta, Clauses, P), ledger_seal(P)
  2. 2The host fetches and re-verifies. A rules block is not a special kind of block and is not treated as one — same hash check, same author check, same signature. ledger_export/0 → ledger_sync/1 → valid_block/6
  3. 3It reads the newest one, or the one in force at a height. A payload that is not rules is skipped, because the chain carries contracts and submissions too. latest_rules/2 · rules_at/3

What comes back is a variant, not the identical term. A payload is text and a clause's variables are local to the clause, so reading it makes fresh ones. That is right rather than a defect — two nodes reading the same payload get clauses that mean the same thing, which is the only sense in which rules can be “the same” across processes.

It also broke the obvious test. Comparing the terms with == reported MANGLED on a perfectly good round trip; the check that replaced it installs what came back and asks it about a real signed block. A term comparison would have been testing the writer.

And this is where the rung's worst bug lived. ledger_export/0 wrapped payloads in hand-written quotes around ~w instead of using ~q. A payload containing a quote therefore came out malformed, the receiving reader stopped early, and blocks vanished with nothing logged.

Rung 2's payloads were prose and never showed it. Rung 7's are source code — a chain publishing its own rules is full of quoted keys — and the first one broke every gossip hop in the aggregator. The symptom, three layers away, was a host that reported having learned chains 0 [].

02

The fence, unchanged, plus one rule

rules_admit/3 = contract_admit/3 + rules_scoped/2

The one rule a contract fence never needed

A contract is alone in its own state. A chain is not. So every predicate a chain defines must be named for that chain: zeta may define zeta_valid/1 and nothing else.

Without it, two chains would both define valid/1 and whichever installed second would answer for both. Worse, a hostile chain could define zeta_valid/1 on purpose and become the authority on somebody else's chain — which is attack_namespace_squat, refused here rather than noticed later.

The namespace check is also where a pillar gap surfaced. “Does this atom start with that one” is written atom_concat(Prefix, _, Name) by anyone, and cocolog raised instantiation_error instead of answering: only the concatenating mode existed, and the two splitting modes ISO 8.16.6 requires were unreachable. Fixed in cocolog on its own merits, with seven regression checks — including that a wrong prefix now fails rather than raising, because guessing wrong about an atom's shape is an ordinary answer.

03

Two regimes, one host, opposite answers

best_foreign/3 — one code path, two chains

And the rules are pinned to a height

A block at height 4 is judged by the rules that were on the chain at height 4, never by the rules published at height 9. That is the difference between a chain that may change its rules — which any chain may — and one that may rewrite what its old blocks meant, which none may. Both readings are defensible until somebody writes one down; rules_at/3 is the one written down.

The last one is the most important line in this rung. psi's published rules are impeccable: they pass the fence, they are correctly namespaced, the signature check is real, and the finality threshold is the same two-thirds rung 6 uses. The host reads them, admits them, installs them and runs them exactly as it runs zeta's.

And every validator on psi is mallory. So a block she signed is a valid block, a head she alone voted for carries all of psi's stake, psi's own psi_final/2 says it is final, and the bridge thaws.

Nothing went wrong. The host verified correctly, under the correct rules, and reached the correct answer to the question it was asked — which was is this final on psi, not is psi honest. An aggregator cannot be stronger than the chains it aggregates, and every bridge that has ever been drained was drained through this door rather than through a broken signature check. Saying so is worth more than one more refusal.

07

Till settlement complete

provenance_across/2 — and unification is the translation layer

A fact imported from a chain keeps the chain's name beside it, and asking where something came from is one findall whose shared variable does the joining:

chainfactsays
zetatrained(d1, alice, 0.99)a model with digest d1 was trained and settled
omegapaid(d1, carol, 100)and somebody paid for it, on a different chain, under a different consensus

No schema mapping and no adapter. Two facts that mention the same digest already agree about it, so the join is the query — which is what the ladder meant by unification is the translation layer.

Settlement never changed shape. It still asks the only question with a checkable answer — does it work — and answers it by re-measuring on the committed holdout. What this rung adds is that the evidence no longer has to live on one chain: a verdict on one chain and a payment on another are one query, and the host that answers it was never told what either chain was.

What this rung does not add

not thiswhy
a rule for admitting a memberany chain whose rules pass the fence can be learned. Which chains a hub is willing to aggregate is a policy question — a certificate, a stake bond, a governance vote — and attack_captured_chain is exactly why that decision matters and exactly why it is not a technical one.
rule upgrades across a forkrules_at/3 pins by height on one chain. Which rules apply to a block on a chain that forked at a rules change has more than one defensible answer, and none of them is written down here.
moving anythingthe bridge thaws. What an escrow releases, to whom, and what happens if the source chain later reorganises below its finalised block are asset questions; this rung is about the proof.
