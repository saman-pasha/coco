The Coco · rung 5

Tick to Settlement

A proof-of-history spine, traced from thirty-two zero bytes to a settled verdict — every function it passes through, in the order it passes through them, and which process runs which goal. Production is one core in a straight line; checking is everybody at once, and that asymmetry is the only reason a spine is worth having.

The one rule that shapes all of it: h(n+1) = sha256(h(n)), over the raw 32 bytes. To know h(n) you must have computed the n−1 hashes before it. There is no shortcut through a hash chain — and winding one backwards means finding a preimage. Everything below is that sentence, arranged.

01

The tick, and the fold

poh_run/3 · poh_mix/3 — library(spine), in C

A spine has exactly two operations. Tick: hash the last hash. Mix: hash the last hash concatenated with an event. Both are 32 bytes in, 32 bytes out, and both live in C because a tick through the module seam — a goal, an atom intern and a 64-character atom — costs about 600 µs, against a hash over 32 bytes when it is a loop.

Mixing is what makes a spine useful rather than merely expensive. A sequence of hashes nobody put anything into proves that somebody hashed a lot. A sequence with an event folded in at tick n proves that the event existed by tick n, and that is a claim anyone can check by re-running the spine.

02

Producing, and publishing the checkpoints

spine_produce/2 → poh_segments/4 → poh_checkpoints/4

The producer runs the loop once, start to finish, and while it runs it keeps every Every-th hash. Those checkpoints are the entire difference between a spine that only its author can check and a spine the whole federation can check at once — without them, the only way to verify N ticks is to redo all N in order.

  1. 1Start from genesis. Thirty-two zero bytes, the same shape as the ledger's genesis parent. poh_genesis(G)
  2. 2Split the range before running it. Every is N // K, and the module walks the whole range emitting a hash every Every ticks — the start counts as checkpoint zero, so K segments come back from K+1 points. poh_segments(G, N, K, Segs) → poh_checkpoints(G, N, Every, Points)
  3. 3Each segment is self-contained. seg(Index, Start, Ticks, End) — everything a verifier needs and nothing about any other segment. That independence is the design, not a convenience. build_segs/4
  4. 4Write them down. The segments become clauses, and the head is a clause too. A node holds no memory between invocations, so anything not written is gone. assertz(spine_seg(I,A,T,B)) · assertz(spine_head(N,End))

This stage cannot be split, and no amount of hardware changes that. Tick k+1 needs tick k’s output as its input; a second core has nothing to do until the first has finished. The producer’s cost is paid once, in order, by one party.

03

What exists after each stage

the data flow, as rows

Every stage’s output is a clause in a knowledge base. There is no daemon, no shared memory and no message passing anywhere in this rung: a verifier is an ordinary cocolog invocation that reads one row, does arithmetic, and writes a verdict.

Because the K verifiers touch K disjoint rows, they never need to hear about each other — which is what lets them run on K machines exactly as easily as in K processes on one.

04

The asymmetry, measured

spine/run.sh — 32,000,000 ticks, 4 segments

Reporting 2.8× without the trend would have been true and misleading. The number moves with the ratio of work to overhead, so the trend is the measurement: at 12M ticks the same script reads 1.8×, at 32M it reads 2.8×, and the gap to 4× is four processes starting up, not four cores failing to divide the work.

The verifiers write nothing the others read, which is why the shell can simply background four invocations and wait. There is no barrier, no leader and no protocol: the parallelism is a consequence of the data shape, not a feature that had to be built.

05

Segments verifying is not the spine verifying

spine_sound/0 → chains/1

Four perfectly good segments that were never one sequence pass a segment-by-segment check. Each one really does run from its start to its end in its stated number of ticks — that is real work, honestly done, on four unrelated spines.

spine_sound/0 sorts the segments by index, verifies every one, and then checks the joins: segment i’s end must be segment i+1’s start, compared with ==. The splice attack is precisely what happens when nobody does that.

06

Anchoring, and why a backdate cannot be hidden

anchor_block/1 → poh_anchor/3 → poh_mix/3

anchor_block/1 reads the current head with current_head/2, folds the block hash in with poh_anchor/3, and asserts both the anchor and the advanced head. From that tick on, every hash in the spine depends on that block having existed — which is what “timestamped” means here, and it is a statement about order, not about the time of day.

07

mallory attacks the clock

spine/mallory.pl — four refused, one accepted

There are no signatures in a spine, so there is nothing for her to forge. Everything she can try is an attack on order, because order is the only thing a spine sells: be paid for work she did not do, or claim an event happened earlier than it did.

attackwhat she trieswhat answers itoutcome
attack_skipclaim a million ticks with a hash she inventedpoh_verify/3 — there is no shortcutrefused
attack_shortendo 900 ticks, claim 1000the count is checked, not labelledrefused
attack_backdatefold at 500, claim tick 10the fold’s own hash; anchor_genuine/1 checks itrefused
attack_splicepaste a genuine segment from another spinechains/1 — the join is the lierefused
attack_forktwo spines from one genesisnothing here, and nothing canACCEPTED

The fork succeeds and is supposed to. Two spines from the same genesis, differing only in what was mixed in, both verify. Both are real work, and no amount of hashing will make a hash chain prefer one sequence over another.

That is not a hole in the implementation; it is what a clock is. A spine orders what is on it. Which spine is the chain’s is the ledger’s question, and poh_anchor/3 is the seam where it gets handed over.

08

Till settlement complete

where rung 5 hands back to rungs 2–4

The spine does not settle anything by itself. It takes a hash the ledger already produced, gives it a position nobody can move, and hands the sequence back. From there the arc is the one traced in Seal to Settlement.

The payload under all of it never changed shape: a contract’s source, or a training submission whose weights travel as chunked rows and whose digest is the join. Settlement asks the same question it always did — does it work — and answers it by re-measuring on the committed holdout, never by believing a worker’s claim.

What the spine adds, and what it does not

It adds a total order that costs work to produce and is cheap to audit, so “this submission was on the chain before that one” stops being a matter of whose clock you trust. Three things it does not add:

not thiswhy
a proof of wall-clock timea faster machine ticks faster. “A million ticks apart” is a lower bound on work, not a reading of the time of day — anyone quoting a spine in seconds is quoting the producer’s CPU.
a proof of whothere is no identity in a spine. The signature is in the block, one rung down; the spine only says when that block appeared relative to everything else.
a fork choicetwo honest spines both verify. Choosing between them is better_head/2’s job, and it always was.

One seam is built and checked but not yet wired through. anchor_block/1 takes any block hash, and the suite proves that two anchored blocks come back in the order they went in and that a backdated anchor is caught. But rung 4’s provenance/1 still answers with the worker, the digest, the measured accuracy, the height and the author — no tick. Anchoring settlement blocks as they are sealed, so that provenance carries a position as well as a height, is a change to rung 4 and has not been made.
