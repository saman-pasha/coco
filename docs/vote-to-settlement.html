The Coco · rung 6, from the vote's side

Vote to Settlement

One vote, traced from the text that gets signed to the verdict it settles — who sends it to whom, every check it survives on the way, and what it leaves behind in each validator's rows. There is no round timer, no leader announcement and no daemon: a validator is an invocation that reads rows, casts one vote and exits.

A validator is not a process that runs. It is a cocolog invocation that reads rows, casts one vote and exits. What another validator has voted is a row it can read — which is why a certificate can be assembled by anyone at all, why there is no aggregator role, and why two nodes holding the same votes build the same certificate.

The signature itself is deterministic: library(secp256k1) derives the nonce with RFC 6979 from the key and the hash, so two validators signing the same vote produce the same signature and there is no entropy source to be wrong.

02

Every check a vote survives

valid_vote/1, then qc_valid/1 — in the order the code applies them

The same gauntlet runs in three places, and that is the point of it being a predicate rather than a step in a protocol: when a validator receives gossip (votes_sync/1), when it verifies a prevote quorum before changing a lock (learn_pol/3), and when anyone at all assembles a certificate (gather/5 → qc_valid/1).

A peer's word that a signature is good is a claim. votes_sync/1 re-verifies every offered vote before it becomes a row — and skips the ones that fail rather than refusing the batch, because a batch containing one bad vote is not a bad batch.

The lock is append-only like everything else: a released lock is replaced by a new row at a higher round rather than by an edit, so what a validator was bound to and when is still on the record. current_lock/2 takes the highest round at that height.

04

Safety and liveness are not the same property

and only one of them is built

Safety is nothing bad happens: no two conflicting blocks are ever both finalised, and if they somehow were, the validators responsible are named. Liveness is something good eventually happens: the chain keeps making progress. They are answered by different mechanisms and this rung answers one of them.

Safety — built and checked

  • The lock. A precommitted validator is bound until a later prevote quorum releases it — locked_ok/5, five clauses, six checks in the suite.
  • The threshold. Q = 2T/3 + 1, so two quorums share more than T/3. Not a convention: arithmetic.
  • Accountability. culprits/3 names the overlap; equivocation/3 returns the two documents one key signed.
  • Finality. extends_final/1 — a chain omitting a finalised block is not a candidate at any length.
  • Atomicity. The vote and the lock are one goal, so one transaction.

Liveness — not built, and not pretended

  • No round timer. Rounds advance because the choreography advances them. Nothing decides that a proposer is late.
  • No round advance. There is no goal that moves a validator from round R to R+1; the round is an argument the caller passes.
  • No nil vote. A validator that will not vote for a proposal simply does not vote, so a failed round is indistinguishable from a slow one.
  • Leader down ⇒ nothing happens. Nobody proposes, proposal_ok/2 fails for everyone, no quorum forms, nothing is finalised — and nothing is wrong, which is exactly the problem.

The honest form of a clock here is rung 5's spine, not wall time. Deciding that a proposer is late needs a measure of elapsed work that every validator computes the same way, and a wall clock is not one — two validators disagreeing about the time is how a timeout becomes a fork. poh_anchor/3 is the seam that would carry it, and joining the two is a rung that has not been built.

Settlement never changed shape. It still asks the only question with a checkable answer — does it work — and answers it by re-measuring on the committed holdout, never by believing a worker's claim.

What the vote buys it is one thing: the chain it reads is no longer merely the deepest one anybody happened to see. “This submission was on the chain” stops being a fact that can be revised, so a verdict computed over a finalised prefix does not have to be recomputed when a longer fork turns up next week — which, as the swimlane shows, it will.

And the vote itself is a row. Not a message that was consumed, not an event that was processed — a clause, sitting in a knowledge base, still readable and still checkable by anybody who wants to re-run qc_valid/1 over it a year from now. The audit is not a log of what the system decided; it is the same data the decision was made from.
